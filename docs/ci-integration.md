# CI 集成

## 1. 目标

AstroPaper 成功生成、校验、构建、提交并推送符合条件的文章后，CI 应将这篇**完全相同**的文章同步到微信公众号草稿箱。

CI 操作只创建草稿，不会向订阅者群发或发布文章，也不会更新已创建的草稿。

## 2. 现有 AstroPaper 工作流

现有的可复用工作流 `.github/workflows/blog-publish.yml` 已经会：

1. 生成定时内容。
2. 写入包含各任务文章路径和状态的 `scheduled-posts-result.json`。
3. 上传结果和生成构件。
4. 校验并格式化生成的 Markdown。
5. 构建 Astro 站点。
6. 提交并推送生成的内容。

该结果清单是微信任务的首选输入。重新计算 Git diff 的精确性较低，特别是当一个分组任务创建多篇文章时。

## 3. 必需的任务顺序

预期顺序如下：

```text
生成并校验
        |
        v
构建 Astro 站点
        |
        v
提交并推送源文章
        |
        v
同步微信公众号草稿
```

在源提交持久化前发布，可能会为从未进入仓库的内容创建草稿。

微信同步应是依赖既有生成任务的独立 job，跑在普通托管 runner 上。它应下载生成结果构件、检出最新分支头部、选择符合条件的结果路径，并调用该包的 CLI；CLI 的微信请求经固定 IP 主机上的转发代理发出。

可直接使用的 job 示例见 [`examples/github-workflow.yml`](../examples/github-workflow.yml)。

## 4. 触发策略

### 4.1 定时生成的文章

微信 job 必须由当前可复用发布工作流显式调用。生成的提交使用仓库 `GITHUB_TOKEN` 推送，而 GitHub 有意不会为该推送再启动工作流。

### 4.2 人工撰写或手动编辑的文章

可通过独立的可信分支 push 工作流检测变更的 Markdown 文件并调用 `publish-changed`，但仍必须要求 `wechat.enabled: true`。

### 4.3 Pull request

Pull request 可以执行检查、渲染和预览构件生成，但绝不能获得微信凭据或调用草稿同步。

### 4.4 手动恢复

手动工作流应接收一个或多个文章路径，并支持：

- 正常同步：已创建过的文章跳过
- CI job 失败后的重试，包括结果不明超时后的协调
- 仅在明确请求时为已同步文章再建一份草稿

不提供强制更新，因为首个版本没有更新路径。已发布草稿需要改动时，在公众号后台直接编辑。

## 5. 文章选择

对于 `scheduled-posts-result.json`，选择满足以下条件的结果：

- 文章路径非空
- 不是任务失败
- 指向已配置内容目录下的 Markdown
- 解析后仍位于已检出仓库内
- 通过 frontmatter 校验
- `draft` 为 false
- `wechat.enabled` 为 true
- 按技术设计第 6.1 节的优先级规则满足配置过滤条件

文章生成此前标记为 `skipped` 的结果，在先前微信同步失败后仍可能需要协调。是否需要微信操作必须由 CLI 的草稿身份与内容哈希决定，不能只看生成器的 `created` 标志。

## 6. 密钥

CI 需要四个环境密钥：

- `WECHAT_APP_ID`
- `WECHAT_APP_SECRET`
- `WECHAT_PROXY_URL`
- `WECHAT_PROXY_TOKEN`

微信凭据存在于 GitHub。ADR-0005 明确接受了这个代价：换来的是微信协议只有一套实现、一套契约测试。若日后凭据泄露风险变得不可接受，退路是 ADR-0004 的窄接口网关方案，届时前两个变量从 CI 移到网关主机。

代理令牌与微信凭据分开，可以独立轮换。

推荐的 GitHub 配置：

- 在受保护的 `wechat-production` environment 中存储这四个值。
- 仅授予同步 job 只读仓库权限。
- 除非必要，不向生成或预览 job 传递密钥。
- 避免打印完整环境变量或 HTTP 请求 URL。

可复用工作流不会自动获得任意密钥，除非调用方传递它们或使用密钥继承。必须在每一层可复用工作流中检查密钥流向。

## 7. 固定出口要求

微信 API 访问受 IP 白名单约束。GitHub 托管 runner 不提供适合此用途的稳定单一出口 IP，因此微信请求不能从 CI 直接发出。这是整个 CI 自动同步方案的硬前提，不是部署细节。

**已决定：由固定 IP 机器上的转发代理充当微信请求的出口。** 该机器的 IP 填入公众平台白名单；微信协议实现留在 Node，代理只做转发；CI 仍使用 GitHub 托管 runner。完整取舍见 ADR-0005。

代理寄生在该机器上已运行的 `yt_dlp_fastapi` 服务中，并以 git submodule 形式引入本仓库的 `services/yt-dlp-fastapi`。

对 CI 的直接影响：

- 同步 job 跑在普通托管 runner 上，没有自托管 runner 需要维护。
- CI 持有微信凭据与代理令牌四个值。
- 检出时需 `submodules: true`；若代理仓库为私有，还需具备读权限的 token。生成和构建 job 不需要 submodule，可关闭以节省时间。

两条必须清楚的风险：

- **代理访问权就是操作公众号的能力边界。** 因为微信侧有 IP 白名单，即使拿到 AppSecret 也调不通微信；反过来，拿到代理令牌和凭据就能操作账户。代理的路径白名单因此直接限定了泄露后的爆炸半径 —— 其中没有群发接口。
- **代理看得见凭据。** token 请求的 body 里有 AppSecret，`access_token` 在 query 里。代理不存储它们，但一行普通 access log 就会把它们落盘。部署时必须确认反向代理与应用两层都不记录 query 和请求体。

### 7.1 曾考虑的方案：自托管固定出口 runner

即把那台固定 IP 机器直接注册为 GitHub Actions runner。已放弃：自托管 runner 会执行工作流定义的任意命令，让它持有微信凭据等于把凭据暴露给整个工作流的可变内容，包括依赖安装脚本。

它仍是可行退路，但优先级低于 ADR-0004 的窄接口网关。若退回该方案，必须恢复以下约束：只允许可信分支触达、绝不允许 fork pull request、每次任务后清理工作区、仅同步 job 使用该 runner。

## 8. 并发

同一微信账户同一时刻只能运行一个同步 job。定时 AstroPaper 工作流可以创建多篇文章，但其草稿操作应串行执行或使用有界并发。

串行化服务于两件事：

1. 避免并发写入台账和重复创建草稿。
2. 避免 token 互踢。一个账户同一时刻只有一个有效 access token，Node 重新成为调用方后这个问题回来了（ADR-0005 第 7 条）。stable-token 接口是主要缓解，并发组是第二道。

需要注意代理不提供第三道防线：它不理解微信，也就无从按账户加锁。本地手动运行与 CI 同时进行时仍可能互相影响，这一点弱于 ADR-0004 的结构性保证。

CI 并发组应按账户区分，且不得取消正在运行的 job。否则在一个结果不明的草稿请求期间取消任务，可能导致下一次运行创建重复草稿。

## 9. 重复预防与恢复

CI runner 是临时的，因此 job 工作区中的本地状态文件不能是唯一同步记录。

同步机制必须支持：

- 跨检出的稳定源身份
- 判断一篇文章是否已经创建过草稿
- 恢复已有微信草稿标识符
- HTTP 超时且服务器结果未知后的协调
- 在任何上传前计算内容哈希，用于源文章变动时的 drift 警告

首个版本不需要更新草稿，也不需要跨运行的图片上传缓存；理由见技术设计第 2.3 节。

可能的持久化状态策略：

| 策略 | 收益 | 成本/风险 |
| --- | --- | --- |
| 扫描现有微信草稿并按文章 source-URL 字段匹配 | 不修改仓库 | 需分页全量扫描，复杂度随草稿箱大小线性增长；对没有规范 URL 的文章无效 |
| 向仓库提交台账 | 可审计、简单，可保存写入状态 | 增加机器人提交；成功 API 调用与台账提交之间有结果不明窗口 |
| 存入外部数据库或有状态服务 | 协调性强，不修改仓库 | 需要新建并运维一套东西；转发代理是无状态的，不能承担这个角色 |
| 仅使用 CI 缓存/构件 | 容易 | 不足以保证正确性 |

微信草稿没有自定义元数据字段。唯一可从远程恢复的标识符是文章的 source-URL 字段，因此远程扫描是重建和恢复路径，而非常规查找方式。

若选择仓库台账，则通过两阶段写入关闭结果不明窗口：调用微信前记录包含预期源身份与内容哈希的 pending 条目；之后用返回的 media 标识符将其标记为 committed。后续运行发现 pending 条目时，表示上次结果未知，应进行协调而非盲目创建。

CI 缓存或构件可改善性能，但不能作为唯一的重复预防机制。

台账默认位于 `.astro-wechat/ledger.json`，**必须提交回仓库**。两点容易踩：

- 不要把它写进 `.gitignore`。同目录下的 `preview/` 是可丢弃的，台账不是；丢了台账，下一次运行会把所有文章当成新文章重新创建。
- 台账提交要让生成类工作流忽略（提交信息带 `[skip ci]`，或在触发条件里排除该路径），否则同步 job 的提交会触发生成 job，两个工作流互相触发。

这些策略的取舍由 ADR-0002 决定，结论是仓库台账。

ADR-0005 之后固定 IP 主机上只有一个无状态转发端点，因此「放到那台机器上」不再是一个现成选项 —— 要走这条路得先建一套有状态服务。台账留在仓库里还有一个代理给不了的好处：每次同步产生的状态变化都出现在提交历史中，可被 pull request 审查。若日后同步方从单一仓库扩展到多个，这个取舍要重新算。

## 10. 结果报告

CLI 应为每篇文章输出机器可读结果：

- 源路径
- 源标识符
- 标题
- 状态：skipped、created 或 failed
- 跳过原因：已同步、未启用、被配置排除或源为 draft
- 内容哈希，以及是否检测到 drift
- 可用时的草稿 media 标识符
- 经净化的错误类别与信息

首个版本不产生 updated 状态。消费方不应假定状态集合封闭，以免将来加入 update 路径时破坏解析。

工作流应将简洁表格写入 GitHub job summary，并将渲染的预览和机器可读结果作为构件上传。不得上传凭据、token、包含密钥的原始响应或无限制的 token 缓存。

## 11. 失败策略

微信同步失败时，博客源提交仍然有效。微信 job 应显式失败，但不要尝试回滚源提交。

代理不可达是新增的失败模式，且与微信本身的失败必须区分：前者是运维问题，重试通常有效；后者按微信错误类别处理。代理长时间不可用时的降级方式，是在已列入白名单的机器上不配置 `WECHAT_PROXY_URL` 直连运行 CLI，不要为此放宽 CI 的安全约束。

预期恢复流程：

1. 修正代理可用性、代理令牌、微信凭据、IP 白名单、源元数据或资源问题。
2. 可能时仅重新运行失败的同步 job。
3. 同步器协调已有远程状态。
4. 未改变或已经同步的草稿将被跳过。

部分批次应报告每篇文章的成功和失败。某篇文章失败，不能将已经创建的草稿视为已回滚。

## 12. 推出计划

1. 在不提供任何密钥的 CI 中运行 `inspect` 和 `preview`。
2. 部署转发代理，从本地经它调通微信 token 接口，确认白名单与令牌生效，此时不接入 CI。
3. 针对开发账户运行 `publish --dry-run`，在任何写入前确认是跳过还是创建。
4. 向开发账户发布一篇明确选定的测试文章。
5. 启用一个低频定时任务。
6. 在数次运行中验证重试后不产生重复草稿，且已同步文章被跳过。
7. 逐项启用额外的任务类型。
8. 生成文章行为稳定后，增加可信人工 push 同步。
