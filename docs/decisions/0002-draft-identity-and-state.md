# ADR-0002：草稿身份、上传前哈希与持久化状态

- 状态：提议中
- 日期：2026-08-10
- 阻塞：里程碑 3（重复预防）

## 范围

技术设计第 2.3 节决定首个版本不更新已有草稿，只保证一篇 Astro 文章最多对应一份微信草稿。本 ADR 因此只解决重复预防所需的最小状态问题，不设计更新所需的完整幂等机制。

被这一范围排除在外的内容：草稿更新路径、跨运行图片上传缓存、封面素材替换与随之而来的孤儿回收。它们在 update 路径实现时重新进入讨论，本 ADR 的接口定义须为其留出位置。

保留在范围内的是重试安全性：同步失败或超时后重跑，不能产生第二份草稿。这是真实需求，与是否支持更新无关。

## 背景

技术设计承诺一篇 Astro 文章最多对应一份微信公众号草稿：已同步过的文章重复运行不做任何操作，同步失败后重试也不会创建第二份。微信平台的两项特性使这比最初设计预期的更困难。

### 草稿不带自定义元数据

微信草稿仅存储文章字段，没有可记录 Astro 源文件路径或内部标识符的用户自定义元数据位置。列出草稿时会按页返回完整文章。

因此，唯一能在平台中携带稳定标识符的字段是文章的 source-URL 字段。不能依据标题匹配，因为标题可编辑、不唯一且对作者可见。

即使填充了该字段，远程查找仍是一次按页扫描，其成本随曾发布文章数线性增长。对于没有 canonical URL 可写入其中的文章，它完全无效。

### 内容哈希必须先于上传可计算

原始哈希定义包含资源 URL 替换后的已净化 HTML。生成这个输入需要先上传资源。

在当前范围下，哈希只用于在源文章同步后被改动时给出 drift 警告。若哈希需要先上传才能算出，一条纯提示信息就会消耗上传配额，这显然不可接受。

在未来的 update 路径下，同一约束会从「避免浪费」升级为「功能能否成立」：跳过决策依赖哈希，而先上传再判断跳过将使跳过失去意义。现在遵守该约束，等于免费保住了后续的正确性。

### 临时性 CI

GitHub 托管的 runner 不会在任务之间保留任何内容。工作区中的状态文件不能成为已同步内容的记录。

## 决策

### 1. 内容哈希仅从上传前输入计算

哈希输入为稳定源标识符、已校验的标题、作者和摘要、资源引用仍为占位符的已净化 HTML、按顺序排列的正文图片内容哈希、已规范化封面内容哈希、渲染器与主题版本，以及哈希 schema 版本。

上传后的 URL 和微信素材标识符均不参与计算。将真实 URL 替换进 HTML 不得改变哈希。

图片身份以内容哈希而非 URL 进入哈希，因此字节变化可被检测，相同字节不会误报。

首个版本中该哈希的唯一消费者是 drift 警告。跳过与否由是否存在 committed 记录决定，与哈希无关。

### 2. 草稿身份由文章 source-URL 字段携带

同步器将文章的 source-URL 字段设置为规范文章 URL，并将其视为稳定标识符。

没有规范 URL 的文章仍可创建，但会报告其不具备可从远程恢复的身份。它不会自动更新，重新同步时必须显式指定目标。

### 3. 持久化状态存入仓库台账，远程扫描用于恢复

提交到 Astro 仓库的台账文件是稳态记录。它会按文章保存稳定源标识符、写入状态（pending 或 committed）、微信草稿 media 标识符、封面素材标识符、已记录的孤儿封面素材，以及上次同步内容哈希。

图片上传缓存不在台账中，因为首个版本不更新草稿，每篇文章的图片一生只上传一次。台账须定义为状态存储接口的实现，使后续加入上传缓存不必改变调用方。

远程分页扫描仅是恢复路径：用于重建丢失或不完整的台账，或解决含糊的写入结果。它受配置的最大页数限制；达到该上限即报错并要求操作人员介入，而不是静默回退到创建草稿。

### 4. 台账分两个阶段写入

调用微信前，写入包含预期源身份和内容哈希的 pending 条目。调用返回后，使用返回的 media 标识符将条目标记为 committed。

之后的运行发现 pending 条目时，表示上一次结果未知。这会触发与微信的核对，绝不盲目创建新草稿。

这样关闭了成功 API 调用和台账提交之间的窗口，这是仓库台账原本唯一的正确性缺口。

## 后果

### 正面影响

- 已同步文章重复运行不产生任何请求，可通过统计 mock server 请求来测试。
- 常规路径由本地状态、结果不明路径由核对来防止重复草稿。
- 台账可在普通 pull request 中审查，且不为状态另建基础设施。ADR-0005 的转发代理是无状态的，本来也承担不了这个角色。
- 孤儿封面素材成为有记录的事实，而非无声的配额泄漏。
- 作者改动已同步文章时会收到 drift 警告，而不是一次含义不明的 skipped。

### 负面影响

- 除生成内容的提交外，CI 还会产生台账提交。必须将它们排除在任何把仓库变更视为新内容的机制之外，否则两个工作流会彼此触发。
- 并发运行可能冲突于台账文件。按账户划分的 CI 并发组已经将同步串行化；台账继承这一约束，而非独立解决它。
- 台账会在仓库中记录草稿 media 标识符，这与 frontmatter 合约刻意避免的做法相反。这在专用状态文件中可接受，但在文章 frontmatter 中仍不可接受。
- 仓库台账不适用于未来的多仓库或托管式部署。预计迁移到外部存储会作为统一接口背后的后端变更，因此台账被定义为状态存储接口的一个实现，而非直接文件访问。

## 考虑过的替代方案

### 将远程草稿扫描作为稳态查找

拒绝。成本随草稿箱大小增长，且对没有规范 URL 的文章完全无效。它作为恢复路径保留，但每次运行都全量扫描一遍草稿箱只为回答「这篇发过没有」，代价与收益不成比例。

### 外部数据库或有状态服务

延后，而非拒绝。ADR-0005 之后固定 IP 主机上只有一个无状态转发端点，因此这条路要先建一套新东西，而不是复用现成的。

即便建了也有两条不利：台账留在仓库里，每次同步产生的状态变化都会出现在提交历史中，可被 pull request 审查；放进外部服务后，只有登录那台机器才能知道系统认为哪些文章已发布。同时，该服务宕机会把「无法发布」升级为「无法判断是否发布过」。

若日后同步方从单一仓库扩展到多个，仓库台账将无法协调，届时应迁入独立存储，并同时解决审查性问题。

### CI 缓存或构件

拒绝作为正确性机制。缓存可被清除，缓存未命中会导致重复草稿。它们仍可作为台账之前的性能层。

### 将状态存入文章 frontmatter

拒绝。它将机器状态混入作者编辑的内容，每次同步都会产生嘈杂 diff，并与 frontmatter 合约冲突。
