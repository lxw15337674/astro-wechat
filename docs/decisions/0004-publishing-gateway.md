# ADR-0004：由 Python 发布网关代发微信请求

- 状态：**已被 ADR-0005 取代**
- 日期：2026-08-10
- 取代：ADR-0002 与 CI 集成第 7 节中「采用自托管固定出口 runner」的决定

> **本决策未被实施。** [ADR-0005](0005-forwarding-proxy.md) 改为让微信协议实现全部留在
> Node，Python 侧退化为一个不理解微信的转发代理。反转的理由是本文档「负面影响」里
> 自己列出的那条：两套 mock 契约需要手工同步，成本高于它换来的凭据隔离收益。
> 本文第 2 节提出的 submodule 耦合也未采用；当前父项目只配置独立代理的服务地址。
>
> 保留本文档，是因为它记录了「窄接口 + 凭据隔离」这条路的完整论证。若日后凭据泄露
> 风险变得不可接受，或同步方从单一仓库扩展到多个，应该回到这里。

## 背景

微信接口受 IP 白名单约束。GitHub 托管 runner 的出口 IP 段轮换，无法列入白名单。

此前的结论是使用自托管 GitHub Actions runner，把那台固定 IP 的机器直接变成 CI 执行环境。现在改变方向：那台机器上已经运行着 `yt_dlp_fastapi` 服务，把微信调用做成该服务上的一组接口，比把它改造成 CI runner 更合适。

反转的理由不只是省事：

- 自托管 runner 会执行工作流定义的任意命令。让它持有微信凭据，等于把凭据暴露给整个工作流的可变内容，包括依赖安装脚本。
- 微信 AppSecret 此后完全不需要存进 GitHub。CI 只持有一个可随时轮换的网关令牌，泄露后的爆炸半径小得多。
- 一个账户同一时刻只有一个有效 access token。网关成为唯一的微信调用方后，token 互踢问题从「靠并发组约束」变成结构上不可能发生。

代价是引入一个需要独立运维的系统，以及项目跨两种语言。

## 决策

### 1. 全部微信调用由网关发起

Node 侧不直连微信，也不持有微信凭据。CLI 完成解析、渲染、资源规范化、哈希和状态管理后，通过网关完成需要外部写入的部分。

### 2. 网关以 git submodule 引入本仓库

路径：`services/yt-dlp-fastapi`，指向 `https://github.com/lxw15337674/yt_dlp_fastapi.git`。

这样安排使端点契约和它的实现在同一次提交中可见 —— 改契约时能一眼看到两侧是否同步。代价是两个发布节奏不同的项目产生耦合，且克隆本仓库的人会额外拉取一个与 Astro 无关的服务。

约束：

- npm 包的 `files` 字段只含 `dist`，submodule 不会进入发布产物。
- Node 代码**不得** import submodule 中的任何内容。它是部署产物的来源，不是构建依赖。
- CI 检出时需 `submodules: true`；若该仓库为私有，还需提供具备读权限的 token。
- 只在需要改动网关时更新 submodule 指针，并在提交信息中说明契约是否变化。

### 3. 端点是窄接口，不是通用代理

一个转发任意微信请求的代理，等于把账户的全部能力交给持有网关令牌的人。端点因此按用途逐个定义，只覆盖同步草稿真正需要的操作。

| 端点 | 用途 | 返回 |
| --- | --- | --- |
| `POST /wechat/body-images` | 上传正文图片 | 图片 URL |
| `POST /wechat/covers` | 以永久素材上传封面 | `media_id` |
| `POST /wechat/drafts` | 创建草稿 | `media_id` |
| `GET /wechat/drafts/by-source` | 按文章 source-URL 字段查找草稿，用于协调 | `media_id` 或空 |
| `DELETE /wechat/materials/{media_id}` | 删除孤儿封面素材 | 无 |

**不暴露**群发、发布到订阅者、修改账户设置、以及任何未在上表中列出的能力。首个版本不实现草稿更新端点，与技术设计第 2.3 节一致。

`DELETE` 端点默认由配置开关关闭。删除素材不可逆，而清理孤儿是低频的手工运维动作，不值得让它长期可达。

分页扫描草稿在网关内部完成，Node 侧只看到一次查询。扫描页数上限由网关配置，达到上限返回明确错误而非空结果 —— 空结果会被 Node 侧误解为「没发过」，进而重复创建。

### 4. 认证与加固

- 请求携带 Bearer 令牌，与配置值做常量时间比较。
- 仅接受 HTTPS。
- 除令牌外，尽可能在网络层限制来源。GitHub 托管 runner 的来源 IP 不可预测，因此令牌是主要防线，这一点必须清楚：**任何能拿到该令牌并访问到网关的人，都可以向你的公众号草稿箱投稿。**
- 令牌与微信凭据分开配置，令牌轮换不需要动微信凭据。
- 限制请求体大小，上限与微信各接口的限制一致，避免网关成为放大器。
- 同一公众号的写操作在网关内串行。
- 日志不得记录令牌、AppSecret、access token，以及包含它们的完整响应。

### 5. token 与配额在网关

access token 的获取、缓存和刷新只发生在网关。它是唯一调用方，因此使用 stable-token 端点仍然正确，但 token 互踢已不可能发生。

微信接口配额的观测点也在网关。配额耗尽必须作为独立错误类别返回给 Node 侧，且不重试，与技术设计第 9 节一致。

### 6. 职责边界

| 环节 | 位置 |
| --- | --- |
| 项目发现、frontmatter 解析、字段校验 | Node |
| 资源解析、SVG 栅格化、图片规范化 | Node |
| Markdown 渲染、链接改写、净化、CSS 内联 | Node |
| 内容哈希与 drift 判断 | Node |
| 草稿身份台账、pending/committed 写入 | Node（仓库台账，见 ADR-0002） |
| access token、素材上传、草稿创建、草稿查找 | 网关 |
| 微信错误码分类与配额识别 | 网关产生，Node 消费 |

图片字节由 Node 规范化后上传给网关，网关只做转发和错误翻译，不做图片处理。这样图片规则只有一处实现，且能在没有网关的情况下测试。

## 后果

### 正面影响

- 微信 AppSecret 不再进入 GitHub，CI 只持有可轮换的网关令牌。
- CI 回到托管 runner，不必维护一台可执行任意工作流命令的自托管机器。
- token 互踢在结构上消失。
- 网关的接口面窄且固定，比通用代理更容易审计。

### 负面影响

- 多了一个必须保持在线的系统。网关宕机时同步失败，但博客发布不受影响（CI 集成第 11 节）。
- 项目跨两种语言，测试和依赖各一套。
- 微信调用无法在纯 Node 的测试中端到端验证。Node 侧对网关做契约测试，网关侧对微信做契约测试，两套 mock 的契约必须手工保持一致 —— 这是本决策引入的主要长期成本。
- 把微信端点加进一个原本做视频下载的服务，会让该服务的职责变杂。若日后端点增多，应拆为独立服务。

## 考虑过的替代方案

### 自托管固定出口 runner

即此前的决定。反转原因见背景：凭据暴露面更大，且需要维护一台执行任意工作流命令的机器。它仍是可行退路 —— 若网关运维成本超出预期，可以退回这个方案，Node 侧只需把网关客户端换成直连客户端。

### 在 Node 侧写一个同样的网关

不采用。固定 IP 的机器上已有 Python 服务在运行，再引入一个 Node 常驻进程只会多一套部署和监控。

### CI 不发布，改为本地手动运行 CLI

不采用。这会放弃「定时生成后自动同步」这个核心目标。但它是网关不可用时的可行降级方式，值得写进运维文档。
