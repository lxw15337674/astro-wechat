# ADR-0005：用固定 IP 主机上的转发代理满足微信 IP 白名单

- 状态：提议中
- 日期：2026-08-10
- 取代：ADR-0004

## 背景

微信接口受 IP 白名单约束，GitHub 托管 runner 的出口 IP 段轮换，因此微信请求不能从 CI 直接发出。这个前提没有变。

ADR-0004 的解法是把微信调用整体搬到固定 IP 主机上的 Python 服务里，暴露五个按用途定义的窄接口。它有一条被自己列为「主要长期成本」的负面后果：

> 微信调用无法在纯 Node 的测试中端到端验证。Node 侧对网关做契约测试，网关侧对微信做契约测试，两套 mock 的契约必须手工保持一致。

实际权衡后认为这条成本过高。微信协议的知识——错误码分类、`errcode` 藏在 HTTP 200 里、配额语义、token 生命周期——会被切成两半分散在两种语言中，而这些恰恰是最容易写错、最需要集中测试的部分。为一个单人博客的发布流程维护两套需要手工同步的契约，不划算。

## 决策

### 1. 微信协议实现全部留在 Node

Node 侧构造完整的微信请求：token 获取、图片上传、永久素材上传、草稿创建、草稿查找。响应解析、`errcode` 检查、错误分类、配额识别、重试判定，全部在 Node。

固定 IP 主机上的服务不理解微信，只是一段网络路径。

### 2. Python 侧只做转发

固定 IP 主机上的独立服务只提供一个转发端点：接收请求、转发到微信、原样返回上游响应。它不解析响应体，不认识 `errcode`，不持有凭据。

父项目仅通过 `WECHAT_PROXY_URL` 与 `WECHAT_PROXY_TOKEN` 使用已部署端点，不引入代理仓库、源码或运行时依赖。代理可以寄生在现有服务中，也可以独立部署，只要满足契约。

契约见 [转发代理契约](../proxy-contract.md)。

#### 为什么不复用已有的 `/v1/proxy`

该服务已经有一个通用转发端点 `/v1/proxy`（`app/proxy.py`），带 Bearer 认证、SSRF 防护（拒绝解析到非公网地址的目标）、重定向上限与逐跳头剥离。看起来正好够用，但有三条不适配，其中第一条是硬阻塞：

1. **它不支持 multipart 请求体。** `build_upstream_body` 只处理字符串和 JSON，二进制会被 JSON 序列化。图片和封面上传是 `multipart/form-data` 二进制，走不通。要复用就得把通用代理改造成能透传任意二进制体 —— 那是在放宽一个通用组件的能力边界，去迁就一个特定调用方。
2. **目标可以是任意公网 URL。** 本决策第 3 条的价值正在于目标固定加路径白名单：因为微信侧有 IP 白名单，代理访问权就是操作公众号的能力边界。通用代理把这条边界打开了 —— 拿到令牌的人可以从这台机器访问任何公网地址，包括微信的群发接口。SSRF 防护挡的是内网，不是这个。
3. **令牌共用。** `/v1/proxy` 用服务级的 `API_AUTH_TOKEN`。共用意味着微信发布能力和 yt-dlp 抽取能力绑在同一个令牌上，轮换其一即轮换全部，且任一泄露都波及另一方。

因此增加一个独立的 `/wechat/*` router，用独立的 `WECHAT_PROXY_TOKEN`。它与 `/v1/proxy` 并存，互不影响。

### 3. 目标主机固定，路径按白名单

代理**不从请求中读取目标主机**。目标固定为 `api.weixin.qq.com`，写在代理配置里。

路径同样按白名单放行，默认只包含同步草稿实际需要的几条。

这两条不是可选的加固项，而是这个设计能否成立的前提：

- 一个能转发到任意主机的代理就是开放代理。别人可以借这台机器的 IP 攻击第三方，或者把请求指向内网地址做 SSRF。这台机器还跑着别的服务，内网可达面不为零。
- 因为微信侧有 IP 白名单，**这个代理本身就是「能否操作你的公众号」的能力边界**。即使攻击者同时拿到 AppSecret 和 access token，没有代理访问权也调不通微信。路径白名单因此直接限定了泄露后的爆炸半径：白名单里没有群发接口，泄露就变不成群发。

### 4. 认证与加固

- 请求携带 Bearer 令牌，常量时间比较。
- 仅 HTTPS。
- 只放行 GET 与 POST。
- 不跟随重定向。
- 请求体与响应体大小设上限。
- **绝不记录 query string 和请求体。** 微信把 `access_token` 放在 query 里，token 请求的 body 里有 AppSecret。代理虽然不存储凭据，但它看得见 —— 一行 access log 就能把它们落盘。

### 5. 允许直连回退

代理地址未配置时，客户端直连 `api.weixin.qq.com`。

在已列入白名单的机器上本地调试时这是最短路径，也让代理故障时有一条不需要改代码的应急通道。CI 必须配置代理，因为托管 runner 直连必然失败。

### 6. 凭据位置

`WECHAT_APP_ID` 与 `WECHAT_APP_SECRET` 回到调用方，也就是 CI 与开发者机器。

这是本决策放弃的东西，必须写清楚：ADR-0004 的主要安全收益就是 AppSecret 不进 GitHub，现在放弃了。仓库或 CI 被攻破时，攻击者拿得到公众号凭据。

缓解措施只能是常规做法，不能等价替代：凭据存在受保护的 environment 中、只暴露给同步 job、定期轮换、不打印完整环境变量。

代理令牌与微信凭据仍然分开，因此代理令牌可以独立轮换。

### 7. access token 的并发

Node 重新成为微信调用方，token 互踢的可能性随之回来：一个账户同一时刻只有一个有效 token，普通 token 接口的获取会使旧的失效。

因此仍然使用 stable-token 接口，并保留按账户划分的 CI 并发组。需要明确的是本地手动运行与 CI 同时进行时依然可能互相影响，这一点弱于 ADR-0004 的结构性保证。

## 后果

### 正面影响

- 微信协议只有一套实现、一套测试。mock 直接扮演微信，测的是真实契约而不是我们自己发明的中间契约。
- 代理侧极小且几乎不变。改微信调用通常不需要改代理，也不会产生仓库指针耦合。
- 代理可复用：将来别的项目需要从固定 IP 调用微信，同一个端点即可。
- 保留直连回退，本地调试与应急都不依赖代理。

### 负面影响

- AppSecret 回到 CI。这是相对 ADR-0004 的实质性倒退，见第 6 条。
- 代理能看见凭据与 token，即使不存储。日志策略从「最好别记」升级为「记了就是泄露」。
- token 互踢的防线从结构性保证退回为约定。
- 请求多绕一跳，上传大图片时延迟与失败面都变大。代理的超时与体积上限必须与微信接口的限制对齐，否则会在自己这一层制造出微信不会返回的错误。

## 考虑过的替代方案

### ADR-0004 的窄接口网关

即被本决策取代的方案。它的凭据隔离更好，接口面更窄更易审计。放弃的原因是两套契约的同步成本，见背景。

若日后同步方从单一仓库扩展到多个、或凭据泄露风险变得不可接受，应该回到这个方案。届时 Node 侧的改动是把微信客户端换成网关客户端，渲染与状态部分不受影响。

### 自托管固定出口 runner

ADR-0004 已评估并放弃：自托管 runner 会执行工作流定义的任意命令，让它持有微信凭据等于把凭据暴露给整个工作流的可变内容。该结论不受本决策影响。

值得注意的是，本决策把 AppSecret 放回 CI 后，这条理由的相对分量下降了 —— 凭据已经在 GitHub 的可变环境里。自托管 runner 仍然更差，因为它同时暴露一台长期在线的机器。
