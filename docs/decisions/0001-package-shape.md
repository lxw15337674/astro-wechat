# ADR-0001：一个包含核心库、CLI 和 Astro 集成的 npm 包

- 状态：提议中
- 日期：2026-08-10

## 背景

该工具必须能自然地集成 AstroPaper、在 GitHub Actions 中显式运行，并可供普通 Node.js 程序使用。若从 Astro 构建钩子发布，会把外部副作用耦合到本地、预览和 CI 环境中可能重复运行的构建中。

在公共接口尚未稳定前，将首次实现拆分为多个独立版本化的包，会增加发布和依赖管理开销。

## 决策

构建一个以 Node.js 22+ 为目标的 ESM npm 包。

该包将提供：

1. 作为默认导出的、与框架无关的核心库。
2. 用于检查、预览和显式草稿同步的 CLI 二进制程序。
3. 位于独立子路径的可选 Astro 集成，用于项目发现、校验和预览支持。

核心库而非集成作为默认导出，确保从普通 Node.js 或 CI 使用方导入此包时，不会加载依赖 Astro 的代码。

Astro 集成绝不会在 `astro dev`、`astro sync` 或 `astro build` 期间自动发布。

包名确定为 `@lxw15337674/astro-wechat`；已通过 npm 登录身份和现有包的 `read-write` 权限核验个人 scope 所有权。

## 后果

### 正面影响

- 只需一次安装和一个版本号。
- 可在无需 Astro 或微信凭据的情况下测试核心行为。
- CI 可调用稳定的非交互式 CLI。
- 其他静态站点项目稍后可复用核心库。
- 发布保持显式且可审计。

### 负面影响

- 包清单必须描述多个入口。
- Astro 专用依赖与框架无关依赖需要谨慎隔离。
- 集成可能需要将 Astro 声明为可选 peer dependency，而 CLI 不需要。
- 在接口稳定后，未来生态发展可能有理由拆分包。

## 考虑过的替代方案

### 从 Astro 构建钩子发布

拒绝。构建是可重复操作，而草稿同步是外部副作用。这还会在预览部署中产生凭据泄露和重复草稿风险。

### 只构建独立 CLI

对于首次实现可行，但无法提供 Astro schema、项目发现，或未来开发预览的集成能力。尽管也会提供集成，CLI 仍是实际操作入口。

### 以核心库、CLI 和集成包组成 monorepo 起步

延后。若使用者需要不同的发布节奏或依赖集合，独立包可能会变得有用；但其初始收益不足以抵消维护成本。
